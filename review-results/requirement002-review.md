# 1. 需求摘要

客户可以在手机端发起贷款提前还款申请。客户提交申请后，系统计算应还金额，客户确认金额后完成还款。还款成功后贷款状态更新为已结清；还款失败时，客户可以重新发起申请。后台工作人员可以查看提前还款申请，但需求未明确金额计算规则、支付处理状态及后台访问权限范围。

# 2. P0 — 必须确认的问题

**问题：**

提前还款金额的计算规则待确认，包括计价基准日期、应包含的金额项目，以及客户确认后的金额是否需要在支付期间锁定。

**为什么重要：**

需求事实仅说明系统计算“需要偿还的金额”，未定义金额构成和计算时点。该规则直接决定客户的应付金额、支付订单金额及贷款结清处理。

**不确认的风险：**

现在不确认无法安全设计核心金额计算和支付数据模型，可能发生客户确认金额与实际扣款金额不一致，或结清金额计算错误。

**问题：**

从客户确认金额到支付成功、支付失败及重新发起申请的状态与幂等处理规则待确认，包括支付结果返回延迟或重复返回时应如何处理。

**为什么重要：**

需求明确了成功后结清、失败后可重试，但未定义支付处理中贷款是否仍可再次申请，也未定义同一申请或支付结果被重复处理时的状态规则。

**不确认的风险：**

现在不确认无法安全设计核心还款状态机与结清触发逻辑，可能导致重复支付、重复结清，或支付实际成功但贷款状态未正确更新。

**问题：**

后台工作人员查看提前还款申请的权限范围待确认，例如是否只能查看本人、所属机构或特定职责范围内的申请。

**为什么重要：**

需求仅说明工作人员可以查看申请，未定义数据访问边界。这直接决定后台数据权限和接口鉴权模型。

**不确认的风险：**

现在不确认无法安全设计核心权限模型，可能造成工作人员越权查看客户贷款及还款信息，后续调整将影响后台查询和鉴权逻辑。

# 3. P1 — 建议确认的问题

**问题：**

“提前还款”是否仅指全部结清，是否支持部分提前还款，待确认。

**为什么重要：**

需求以“还款成功后贷款状态更新为已结清”描述结果，可推知当前流程倾向于全部结清；但是否排除部分提前还款并未明确。该范围会影响后续产品能力和金额计算扩展方式。

**问题：**

还款失败后重新发起申请时，原申请和原金额确认记录如何处理，待确认。

**为什么重要：**

这影响申请记录展示、客户重试体验及后台工作人员查看信息的方式，但不改变成功结清的主流程。

# 4. P2 — 后续确认的问题

**问题：**

客户完成还款或还款失败后，是否需要展示或发送结果通知，待确认。

# 5. 核心风险 Top 3

1. 提前还款金额的构成、计算时点和确认后有效性未定义，可能导致应付金额或结清金额错误。
2. 支付成功、失败和重试缺少明确状态及幂等规则，可能导致重复支付或贷款状态与实际支付结果不一致。
3. 工作人员查看提前还款申请的权限边界未定义，可能导致后台数据权限模型错误。

# 6. 最应该问业务方的5个问题

1. 提前还款金额应包含哪些项目，按哪个时间点计算？
2. 客户确认金额后，该金额在多久内有效；金额发生变化时应如何处理？
3. 客户确认金额到支付结果返回期间，申请和贷款分别处于什么状态，是否允许再次发起申请？
4. 支付结果延迟或重复返回时，系统应如何确保只完成一次还款和一次结清？
5. 哪些后台工作人员可以查看哪些提前还款申请，是否需按申请归属、机构或职责限制？

# 7. 评审结论

**需要补充需求后再开发**

理由：金额计算规则、支付结果对应的状态流转及后台访问权限均未明确，直接影响核心金额逻辑、状态机和权限模型。应先确认这些规则，再进入开发。
