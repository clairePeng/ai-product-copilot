# 1. 需求摘要

客户提交贷款申请后，系统检测资料是否完整；资料不完整时提示客户通过手机端补充，补充后可重新提交。后台工作人员可查看资料，若仍不完整可要求客户再次补充。资料完整后，申请进入审批流程。

# 2. P0 — 必须确认的问题

**问题：资料"完整性"的判断标准未定义**

**为什么重要：** 该判断是触发"提示补充"与"进入审批"两个分支的核心业务条件，标准不明确将导致状态转换条件无法实现。

**不确认的风险：** 开发只能凭猜测实现校验逻辑，上线后可能出现误判，导致状态机返工。

---

**问题：资料补充循环缺少终止条件**

**为什么重要：** 客户补充资料后系统重新判断，若仍不完整会再次提示/被工作人员要求补充，业务描述未说明补充次数或超时上限，可能形成"提示补充 → 补充 → 判断不完整 → 再次提示"的无限循环状态。

**不确认的风险：** 状态机可能无法收敛，申请长期停留在"待补充"状态，影响核心流程闭环设计。

---

**问题：系统自动判断与工作人员判断的权限边界不清**

**为什么重要：** 系统会自动检测资料完整性，同时工作人员也可以"要求客户再次补充"，两者判断结果不一致时以谁为准未定义，属于权限模型问题。

**不确认的风险：** 可能导致系统状态与人工操作冲突，返工权限模型设计。

# 3. P1 — 建议确认的问题

**问题：多次补充资料是否需要保留历史版本**

**为什么重要：** 客户可能多次提交资料，是否需要保留每次提交的历史记录会影响数据模型设计。

---

**问题：本需求与审批流程的衔接规则未定义**

**为什么重要：** "资料完整后进入审批流程"仅说明触发时机，审批流程的角色、规则不在本次范围内，但衔接方式（如状态如何传递）会影响系统间数据一致性。

---

**问题：客户长时间未补充资料的处理机制未定义**

**为什么重要：** 影响异常场景下申请单据的最终状态归属，避免申请无限期悬挂。

# 4. P2 — 后续确认的问题

**问题：补充提示的通知方式（短信/App推送/站内信）未定义**

**问题：手机端补充资料的具体交互形式未定义**

# 5. 核心风险 Top 3

1. **资料完整性判断规则不明确** — 该规则是决定申请流转方向的核心触发条件，不确认可能导致业务逻辑返工。
2. **资料补充循环缺少终止条件** — 可能导致状态机设计缺陷，申请无法正常收敛，属于核心状态机风险。
3. **系统与工作人员的判断权限边界模糊** — 可能导致权限模型设计冲突，返工职责划分。

# 6. 最应该问业务方的5个问题

1. 系统如何判断"资料是否完整"？是自动规则校验，还是需要人工审核？
2. 客户补充资料的次数或时限是否有上限？超过后该笔申请如何处理？
3. 若系统判断与工作人员判断的结果不一致，以谁的判断为准？
4. 客户多次提交的资料是否需要保留历史版本以便追溯？
5. 长时间未完成资料补充的申请，是否需要自动关闭或转入其他处理流程？

# 7. 评审结论

**需要补充需求后再开发。**

理由：资料完整性判断标准、补充循环的终止条件、系统与人工判断的权限边界这三项均属于核心业务逻辑/状态机/权限模型层面的问题，且需求描述中没有提供依据，若直接开发存在较高的返工风险。
