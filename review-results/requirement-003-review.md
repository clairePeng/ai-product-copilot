# 1. 需求摘要

医院工作人员发现设备故障后，可提交包含设备信息和故障描述的维修申请。维修人员收到申请后进行维修，完成后填写维修结果并将申请标记为已完成；问题未解决时可继续处理。科室负责人可以查看本部门维修申请，系统需要记录申请的处理情况。需求已描述报修与完成的主流程，但维修申请状态、处理责任及处理记录规则仍待确认。

# 2. P0 — 必须确认的问题

**问题：**

维修申请从提交、维修处理、继续处理到已完成的状态及转换触发条件待确认，包括维修人员发现问题未解决时申请处于何种状态，以及何时允许标记为已完成。

**为什么重要：**

需求事实只定义了“已完成”，并说明问题未解决时可继续处理，未定义处理中、待处理或继续处理等状态及其转换规则。这直接决定维修申请的核心状态机。

**不确认的风险：**

现在不确认无法安全设计核心状态机，可能出现问题尚未解决却被关闭，或申请无法区分待处理与处理中，影响后续处理与统计。

**问题：**

维修人员如何收到、认领或被分配维修申请，以及一张申请是否允许由多名维修人员处理，待确认。

**为什么重要：**

需求仅说明维修人员“收到申请后进行维修”，未明确申请的责任归属和分配规则。这直接决定维修处理权限、待办列表与申请责任人数据模型。

**不确认的风险：**

现在不确认无法安全设计维修处理的核心业务逻辑和权限边界，可能导致多人重复处理、无人负责或维修人员处理无权限申请。

**问题：**

“系统需要记录维修申请的处理情况”的记录内容、记录时点及是否保留历次处理记录待确认。

**为什么重要：**

需求明确需要记录处理情况，但未定义处理过程是否需逐次留存、维修结果是否允许修改及记录与维修申请的关联方式。这直接影响核心处理记录的数据模型。

**不确认的风险：**

现在不确认无法安全设计处理记录的数据结构，后续若需补充多次维修过程或追溯修改记录，可能导致数据模型返工。

# 3. P1 — 建议确认的问题

**问题：**

设备信息由工作人员手工填写还是从既有设备台账选择，以及设备与科室的归属关系待确认。

**为什么重要：**

这影响报修表单设计、设备数据校验及科室负责人查看范围的实现方式，但可在明确核心申请流程后进一步确定。

**问题：**

科室负责人除查看本部门申请外，是否可以查看申请的完整维修结果和处理记录，待确认。

**为什么重要：**

需求明确其可查看本部门申请，但未明确可见数据范围，影响后台展示与信息访问范围。

# 4. P2 — 后续确认的问题

**问题：**

维修申请提交、分配或完成后是否需要向工作人员、维修人员或科室负责人发送通知，待确认。

# 5. 核心风险 Top 3

1. 维修申请缺少从提交到完成、继续处理的明确状态与转换规则，可能导致处理流程无法正确闭环。
2. 维修申请的分配和责任归属规则未定义，可能导致维修任务重复处理、无人处理或权限错误。
3. 处理情况的记录范围与历史留存规则未定义，可能导致核心处理记录数据模型返工。

# 6. 最应该问业务方的5个问题

1. 维修申请在提交、分配、处理中、问题未解决和完成时分别应处于什么状态；各状态由什么事件触发转换？
2. 维修人员是系统自动接收、人工认领还是由人员分配维修申请？
3. 一张维修申请是否允许多名维修人员协同或先后处理；责任人如何确定？
4. 维修人员填写的“处理情况”需要记录哪些内容，是否必须保留每次处理和修改的历史？
5. 设备信息是手工输入还是从设备台账选择；设备与科室的归属关系由哪个系统或数据维护？

# 7. 评审结论

**需要补充需求后再开发**

理由：维修申请的核心状态流转、维修任务的责任归属及处理记录的数据规则均未明确，直接影响状态机、权限边界和数据模型。应先确认这些规则，再进入开发。
