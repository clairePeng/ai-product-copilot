# 1. 需求摘要

客户提交贷款申请后，系统发现申请资料不完整时，需要提示客户补充资料。客户可通过手机端补充资料并重新提交申请，资料完整后申请进入审批流程。后台工作人员可以查看客户提交的资料，并在资料仍不完整时要求客户再次补充。需求描述了资料补充的主流程，但资料完整性的判定、重复补充的状态流转及后台访问边界仍待确认。

# 2. P0 — 必须确认的问题

**问题：**

资料完整性的具体判断规则、系统与工作人员的判定职责，以及两者结论不一致时的处理规则待确认。

**为什么重要：**

需求事实中既有系统发现资料不完整，也有工作人员判断资料仍不完整，但未说明必需资料清单、各自判定环节和最终判定主体。这直接决定资料校验逻辑及申请能否进入审批。

**不确认的风险：**

现在不确认无法安全设计核心业务逻辑和审批准入规则，可能出现资料被系统判定完整但被工作人员驳回，或资料不完整却进入审批的情况。

**问题：**

“待补充、客户重新提交、工作人员再次要求补充、进入审批”等申请状态及转换触发条件待确认。

**为什么重要：**

需求描述了可多次补充的循环，但未定义客户重新提交后是否先由系统校验、是否需要工作人员处理，以及再次要求补充后申请所处状态。

**不确认的风险：**

现在不确认无法安全设计核心状态机，开发可能错误触发审批，或使申请在资料补充流程中无法继续处理。

**问题：**

后台工作人员查看客户申请资料的权限范围待确认，例如是否只能查看本人、所属机构或特定职责范围内的申请。

**为什么重要：**

需求仅说明工作人员可以查看资料，未定义访问范围。这直接决定后台数据权限与接口鉴权模型。

**不确认的风险：**

现在不确认无法安全设计核心权限模型，可能造成客户贷款资料被越权访问，并导致后续大范围调整查询与鉴权逻辑。

# 3. P1 — 建议确认的问题

**问题：**

客户补充资料时，既有资料是覆盖、追加还是允许删除，以及是否需保留历次提交记录，待确认。

**为什么重要：**

这影响资料数据的更新方式、后台查看方式和后续追溯能力，但当前主流程可先按明确的数据更新方案推进。

**问题：**

工作人员要求再次补充资料后，客户应通过何种方式获知具体补充要求，待确认。

**为什么重要：**

这影响手机端交互和是否需要支持消息通知，但不阻塞核心资料补充流程设计。

# 4. P2 — 后续确认的问题

**问题：**

手机端展示缺失资料与补充要求的形式待确认，例如是否需要逐项列明缺失内容。

# 5. 核心风险 Top 3

1. 资料完整性的判断规则和最终判定主体未定义，可能导致审批准入逻辑错误。
2. 多次补充资料缺少明确的状态与触发条件，可能导致申请状态流转错误。
3. 工作人员查看申请资料的权限边界未定义，可能导致数据权限模型错误。

# 6. 最应该问业务方的5个问题

1. 贷款申请资料完整的具体判断规则和必需资料清单是什么？
2. 系统与工作人员分别在哪个环节判断资料是否完整；结论不一致时以谁为准？
3. 客户重新提交资料后，是自动进入审批、先由系统校验，还是必须由工作人员处理？
4. 工作人员要求再次补充后，申请应处于什么状态；客户再次提交后如何恢复处理？
5. 哪些后台工作人员可以查看哪些客户的申请资料，是否需按申请归属、机构或职责限制？

# 7. 评审结论

**需要补充需求后再开发**

理由：资料完整性的判定机制、多次补充的状态流转及工作人员资料访问权限均未明确，直接影响核心业务逻辑、状态机和权限模型。应先确认这些规则，再进入开发。
